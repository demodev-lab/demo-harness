## Purpose

Generate the foundational harness file set for a new project. A harness is the operating layer that controls model behavior from outside the model itself — comprising constitutional documents, contextual execution documents, automated enforcement hooks, and memory and learning artifacts. This skill produces all of these at once so the project begins with a functional operating system rather than an empty repository.

The harness is not documentation for humans to read. It is an operating system that agents execute inside. Every file generated by this skill serves a specific behavioral function: constitutional documents constrain all work, skills scope conditional procedures, hooks enforce mechanically, and memory documents accumulate learning. Generating only some of these leaves the system incomplete.

A harness created by this skill satisfies the Harness Engineering Manual's Quick Introduction Checklist: root `AGENTS.md`, three verification commands, a glossary, one skill, one completion hook, and a failure retrospective document. These six elements form the minimum viable harness. Anything less leaves the project without a functional operating layer.

The core principle guiding generation: short global directives plus detailed documents at the point of need, never long global directives. `AGENTS.md` must remain tight. Depth goes into skills, hooks, and docs.

---

## When To Use

- Starting a fresh repository with no existing governance documents
- Bootstrapping harness governance onto a project that previously had none
- Reproducing consistent operating quality across a new team or codebase
- After the user explicitly says "harness init", "initialize harness", "scaffold harness", "set up harness", or "new project harness"
- When onboarding a new coding agent to a repository that has no operating contract

## Pre-flight Questions

Before generating any files, ask the following three questions. Accept brief answers. Do not proceed without them.

1. **Project name** — used in document titles, glossary headers, and the AGENTS.md preamble
2. **Primary language and stack** — used to populate real verification commands (lint, typecheck, test) rather than placeholders
3. **Team size** — used to calibrate sub-agent guidance in `AGENTS.md` (solo, small team 2–5, larger team 6+)

If the user provides a project brief, README, or package.json, extract answers automatically without prompting.

If the primary language cannot be determined, default verification commands to: `echo "configure lint"`, `echo "configure typecheck"`, `echo "configure test"` — and flag these as requiring configuration before Day 1 ends.

## File Generation Workflow

### Step 1 — Read Templates

Load each reference template from the plugin's `references/` directory before generating output. Templates define the expected structure; generation fills in project-specific values. Never generate a file without first reading its corresponding template — templates encode mandatory section structure that cannot be reconstructed from memory.

Reference paths (resolve relative to `${CLAUDE_PLUGIN_ROOT}/skills/harness-init/references/`):

- `agents-md-template.md` — minimal constitutional document template
- `glossary-template.md` — terminology registry template
- `failure-log-template.md` — recurring failure ledger template
- `skill-template.md` — skill document template (Appendix B format)
- `hooks-template.json` — hooks configuration template
- `completion-checklist-template.md` — pre-completion gate template
- `weekly-review-template.md` — retrospective template (Appendix D format)
- `postmortem-template.md` — incident postmortem template
- `architecture-notes-template.md` — architecture decision record template
- `operating-principles-template.md` — project-scoped operating principles template

### Step 2 — Generate Files

Populate each template with project-specific values gathered in the pre-flight step. Apply the following rules during generation:

**AGENTS.md rules:**
- Keep within 40–60 lines. This is a hard limit.
- Include only rules that apply to every single task. Exclude feature-specific rules, conditional branching, and directory trees.
- The five core directives must appear: solve directly, update docs on contract changes, reuse modules before adding abstractions, verify before claiming completion, no destructive commands without approval.
- Add team-size-specific sub-agent guidance: solo projects need none; teams of 6+ benefit from explicit agent scope boundaries.

**Verification commands:**
- Populate with real, runnable commands for the detected stack. Never leave placeholders.
- Node.js: `npm run lint`, `tsc --noEmit`, `npm test`
- Python: `ruff check .`, `mypy .`, `pytest`
- Go: `golangci-lint run`, `go vet ./...`, `go test ./...`
- Ruby: `rubocop`, `steep check`, `bundle exec rspec`
- Unknown stack: use echo commands and flag for configuration.

**Glossary rules:**
- Define at least three terms using the five-field format from Manual section 7.3: Name, Definition, Differences from related terms, Examples, Prohibited mixed expressions.
- Choose the three most domain-specific or ambiguous terms for the project. Never use generic terms that any developer would know.

**Failure log:**
- Initialize empty with column headers only: Date, Failure Description, Cause Category, Absorption Action, Verification Method.
- Do not add example rows. The log must contain only real entries.

**First skill:**
- Choose the most obviously repetitive task type for the stack. REST API project → "add-api-endpoint". CLI tool → "add-command". Frontend component library → "add-component".
- Use the Appendix B skill template structure: When To Use, Steps, Verification, Common Mistakes.

## File Manifest

| File | Layer | Purpose |
|------|-------|---------|
| `AGENTS.md` | Layer A | Immutable rules applied to all work. Contains the 5 core directives: solve directly, update docs on contract changes, reuse modules, verify before claiming completion, no destructive commands. Maximum 60 lines. |
| `CLAUDE.md` | Layer A | Claude-specific behavioral contract. Mirrors AGENTS.md structure with Claude-syntax formatting. Scopes Claude-specific behaviors such as tool use and response formatting. |
| `docs/glossary/README.md` | Layer D | Terminology registry. Each entry contains: name, definition, differences from related terms, examples, prohibited mixed expressions. Prevents terminology drift and documentation mismatch failures. |
| `docs/failure-log.md` | Layer D | Recurring failure ledger. Columns: date, failure description, cause category, absorption action taken, verification method. Append-only; never delete rows. |
| `docs/operating-principles.md` | Layer D | Project-scoped version of the 10 universal operating principles from Manual section 4, adapted to project language, domain, and team conventions. |
| `docs/architecture-notes.md` | Layer D | Architecture decision records. Format: decision title, context, options considered, decision made, consequences, date. Prevents agents from re-litigating settled decisions. |
| `docs/postmortem-template.md` | Layer D | Incident postmortem template. Sections: timeline, root cause, impact, contributing factors, action items with owners. |
| `skills/<first-skill>/SKILL.md` | Layer B | First contextual execution skill covering the most repetitive task type for this project's stack. Scopes rules and verification steps to that task type only. |
| `.claude/hooks.json` | Layer C | Automated enforcement hooks. Pre-configured with: pre-completion test run gate, lint gate, docs-change check. These enforce the most critical rules mechanically. |
| `docs/completion-checklist.md` | Layer C | Pre-completion gate. Five questions covering: tests run, lint/typecheck run, docs updated, user-visible behavior verified, remaining risks recorded honestly. |
| `docs/weekly-review-template.md` | Layer D | Weekly retrospective template. Sections: repeated failures, harness changes (promote rule / create skill / add hook / update glossary), cleanup actions. |

## Milestone Expectations

### Day 0

Complete before writing any code. The harness must exist before the first commit.

- `AGENTS.md` exists and is within 40–60 lines with at least 5 core rules
- `docs/glossary/README.md` exists with at least 3 defined terms
- All three verification commands (`lint`, `typecheck`, `test`) execute without error on the current codebase
- `docs/completion-checklist.md` is referenced in `AGENTS.md` as the documented pre-completion gate
- Every team member or agent entering the project reads `AGENTS.md` before making changes

### Day 1

Complete when repetitive tasks first appear, before the second instance of any task type is attempted:

- First skill document written and placed under `skills/` covering the repeating task type
- Pre-commit or completion hook active — at least one entry exists in `.claude/hooks.json` that fires before completion is reported
- `docs/failure-log.md` initialized with headers and ready to receive the first entry
- First failure absorbed: whatever went wrong on Day 0 is encoded in the harness before Day 1 ends

### Week 1+

Perform every week thereafter without exception:

- Failure case retrospective using `docs/weekly-review-template.md`
- Extract repeated failure patterns from the failure log — any pattern appearing 2+ times is a promotion candidate
- Decide which patterns to promote: text rule to AGENTS.md, repeated violation to hook, ad hoc procedure to skill
- Delete or abbreviate rules unused for 8+ weeks to prevent harness bloat
- Check that `AGENTS.md` has not grown beyond 60 lines since the last review

## Common Mistakes

- Writing an `AGENTS.md` longer than 60 lines — strip feature-specific rules, conditional branches, and directory maps; those belong in skills and docs
- Leaving verification commands as placeholders (`<your-test-command>`) — always populate with real, runnable commands; placeholder commands are silent failures
- Creating an empty glossary — define at minimum the 3 most ambiguous terms in the project domain; an empty glossary will not prevent terminology drift
- Skipping the hooks file — a harness without at least one automated gate relies entirely on memory and willpower, which are insufficient enforcement mechanisms
- Generating files without reading templates first — templates define mandatory section structure that cannot be reconstructed from memory
- Treating the harness as one-time setup — the harness is a living system; the weekly review cycle must begin in Week 1
